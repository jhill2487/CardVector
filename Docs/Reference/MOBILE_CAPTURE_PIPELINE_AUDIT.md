# Mobile Capture Pipeline Audit

Status: Security-gated architecture audit

Date: 2026-07-13

Starting commit: `df6d9d7b428ce45a11fcf6cef470728a1e8461d7`

## Objective

Inspect the current CardVector web, QR, registry, storage, and desktop conversion implementation before adding mobile capture.

The requested Mobile Capture MVP is blocked by the security gate because the current deployed mobile surface is GitHub Pages only. GitHub Pages is static hosting and is not a secure writable backend for original card images, capture-session metadata, or shared processing queues.

## Security Gate Decision

Do not implement the mobile capture MVP directly on the current GitHub Pages site.

Reasons:

- GitHub Pages is static hosting and cannot provide authenticated, idempotent writes.
- Browser code must not contain GitHub tokens, storage keys, or other credentials.
- Runtime images must not be uploaded into the source repository.
- A public unauthenticated upload endpoint would allow arbitrary third-party writes.
- Original images must be stored as objects, not base64 blobs in registry JSON.

## Smallest Appropriate Backend

Recommended first production-capable option: Supabase.

Why it fits this architecture:

- Adds managed authentication, Postgres metadata, row-level security, and object storage without introducing a custom server.
- Keeps GitHub as source of truth for source code only.
- Stores original images outside Git.
- Provides a simple JavaScript client for the existing static web app.
- Provides a clear path for desktop queue polling through authenticated API calls or a service-role desktop integration.

Alternative: Cloudflare Pages + Workers + R2 + D1.

This is also viable, but it introduces more custom backend code and deployment surface. Supabase is the smaller first step for authenticated CRUD plus object storage.

## Proposed Data Contract

Table: `mobile_capture_sessions`

Required fields:

- `capture_session_id` text primary key
- `etb_location_id` text not null
- `source` text not null, default `MOBILE_WEB`
- `status` text not null
- `created_at` timestamptz not null
- `updated_at` timestamptz not null
- `submitted_at` timestamptz
- `operator_id` uuid
- `operator_name` text
- `source_device` jsonb
- `image_count` integer not null default 0
- `original_image_references` jsonb not null default `[]`
- `conversion_status` text
- `conversion_workstation` text
- `error_message` text
- `schema_version` integer not null default 1

Minimum statuses:

- `DRAFT`
- `UPLOADING`
- `PENDING_CONVERSION`
- `PROCESSING`
- `CONVERTED`
- `FAILED`
- `CANCELLED`

Table: `mobile_capture_images`

Required fields:

- `image_id` text primary key
- `capture_session_id` text references `mobile_capture_sessions(capture_session_id)`
- `storage_bucket` text not null
- `storage_path` text not null
- `original_filename` text
- `content_type` text not null
- `byte_size` bigint
- `sha256` text
- `sequence_number` integer not null
- `created_at` timestamptz not null
- `removed_at` timestamptz

Storage bucket:

- `mobile-capture-originals`

Suggested storage path:

```text
mobile-capture-originals/{etb_location_id}/{capture_session_id}/{sequence_number}-{image_id}.jpg
```

## Proposed API Contract

The static mobile app should use authenticated backend calls only.

Required operations:

- `GET /locations/{etb_location_id}`: read ETB/location display metadata.
- `POST /capture-sessions`: create idempotent draft session for a location.
- `POST /capture-sessions/{id}/images`: request/upload image object metadata.
- `DELETE /capture-sessions/{id}/images/{image_id}`: mark image removed before submission.
- `POST /capture-sessions/{id}/submit`: atomically transition to `PENDING_CONVERSION` after all images are stored.
- `GET /capture-sessions?status=PENDING_CONVERSION`: desktop queue discovery.
- `POST /capture-sessions/{id}/claim`: atomically transition `PENDING_CONVERSION` to `PROCESSING`.
- `POST /capture-sessions/{id}/converted`: mark successful conversion with workstation and staged paths.
- `POST /capture-sessions/{id}/failed`: mark processing failure with error message.

Idempotency requirements:

- Session create uses a client-generated `capture_session_id`.
- Submit is rejected unless at least one non-removed image exists.
- Claim is atomic and succeeds only from `PENDING_CONVERSION`.
- Desktop conversion must not process a session already in `PROCESSING` or `CONVERTED` unless explicitly reset.

## Authentication Requirements

Minimum production requirement:

- Operator login before upload.
- Storage writes scoped to the operator and capture session.
- Public QR pages may remain readable, but `Capture Inventory` must require operator authentication.
- Desktop processing should use a server-side/service credential stored outside Git, or an authenticated operator account with explicit processing permissions.

Supabase-specific requirements:

- Enable Row Level Security.
- Allow operators to create/read/update only their own draft/uploading sessions.
- Allow desktop processor role to list/claim/process pending sessions.
- Deny anonymous writes.

## Deployment Changes Needed

- Add backend project configuration outside source-controlled secrets.
- Add environment-variable injection for public client configuration only:
  - `SUPABASE_URL`
  - `SUPABASE_ANON_KEY`
- Store service-role keys only on trusted desktop/backend environments, never in browser code.
- Keep GitHub Pages deployment for static app if using Supabase directly from browser.
- Add backend migration SQL and storage policies once provider is selected.

## Desktop Queue Integration Plan

Add a focused desktop module after backend selection:

- Discover pending sessions from the backend.
- Show ETB location, session ID, image count, submitted timestamp, and status.
- Claim one session atomically.
- Download images to a portable runtime path:

```text
<USERENVIRONMENT>/MobileCapture/Pending/
<USERENVIRONMENT>/MobileCapture/Processing/
<USERENVIRONMENT>/MobileCapture/Converted/
<USERENVIRONMENT>/MobileCapture/Failed/
```

- Stage originals into the existing Physical Inventory Conversion capture structure or extend conversion to accept a staged folder.
- Preserve the ETB/location assignment.
- Mark `CONVERTED` only after successful handoff.
- Leave original uploads retained.

## MVP Work After Backend Approval

Once a secure backend/storage provider is approved:

1. Add backend migrations, storage bucket, policies, and environment documentation.
2. Extend `Docs/app.js` for authenticated `Capture Inventory` on existing `/location/{etb}/{location}` pages.
3. Add mobile-first draft capture UI using rear camera where supported.
4. Store draft state locally for refresh/interruption recovery.
5. Upload original images to object storage.
6. Submit session into `PENDING_CONVERSION`.
7. Add desktop pending-session queue discovery, claim, download, staging, and status update.
8. Add automated tests for validation, status transitions, queue discovery, staging paths, and older registry compatibility.

## Known Limitations

- No secure writable backend exists today.
- Existing GitHub Pages QR pages cannot show private live inventory without a backend.
- Current Physical Inventory Conversion is local/OBS-first and does not yet accept remote mobile capture sessions.
- Current recognition/CardUploader handoff remains future work by design.
- Existing QR routes should be preserved exactly.

## Deferred Decision

Select the backend/storage provider before implementing mobile capture. The smallest safe recommendation is Supabase Auth + Postgres + Storage.
